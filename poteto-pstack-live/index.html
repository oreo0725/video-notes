Poteto（pstack 作者）：怎麼在 SpaceX 一個月出貨上千個 PR

Host：Matt Pocock ／ Guest：Lauren Tan（Poteto，前 Meta React team、Netflix，現於 Cursor／SpaceX AI）
2026-10-03 · 1:05:36 · 在 YouTube 開啟

全場主軸：一條因果鏈

  1. Verification：給 agent「手和眼睛」，讓它自己驗證自己的工作
  2. 信任階梯：agent 能自我驗證，人才敢放手，從 micromanage 一路往上爬
  3. 環境優先：用 lint、type、framework 慣例和 skill 內附的 CLI，讓 agent 預設就做對
  4. 接起 inner／outer loop：讓 agent 自己從 Slack、Linear、X 拿到 context
  5. 總管 agent：coordinator／chief of staff 負責分派與監督，不自己動手
  6. Agent 自己 merge：人改成事後抽樣 review，發現系統性問題就修環境
貫穿全場的比喻是米其林廚房：從一個人包辦一切的家庭廚師，到負責經營廚房的主廚，再到開連鎖餐廳。

Part 1

你是怎麼爬上信任階梯的？

提問（Matt）你提到越信任 agents，就越能讓它們做更好的事、擴展到更多 agents。你個人是怎麼爬上這個階梯的？到了 SpaceX 之後又怎麼越爬越高？

第一階段：side project 時期（約 2026 年 1–2 月）

  • 她離開 Meta React team 後有點 burnout，休了一個月，結果就去開了一個新的 side project（她自嘲 burnout 的人都會這樣）
  • 她發現自己花好幾個小時在 micromanage 單一一個 agent
  • 當時社群很著迷 orchestration，大家都還在 terminal 裡，人人都在講「我自己做了 custom orchestrator」。她也被這個話題勾住了
  • 她開始寫 skills，但沒辦法衡量一個 skill 到底有沒有效，等於在盲飛，只是迭代得很快
  • 那批 skills 後來成了 pstack 的基礎。原始 repo「poteto noodle」現在還開源，裡面有 skills 和一個 brain 目錄
  • 她當時的核心問題是：怎麼把「自己的能力」抽出來交給 agent，教它寫 code、跑 workflow 都更像她自己

第二階段：加入 Cursor 之後（3 月加入，4 月初開始做這件事）

  • 她被找去處理 agents window 的效能問題（介面非常卡），一開始全部手動看 flame graph、heap snapshot
  • 她又遇到同一個問題：自己是瓶頸，等於是夾在 agent 和 Chrome DevTools 之間傳話的「肉身 proxy（meat proxy）」
  • 她原本把個人的 skills 放掉了，後來發現早期學到的教訓都很有用，特別是驗證和工作要嚴謹
  • 原因是 frontier models 也很愛走捷徑。所以她的 skills 都圍繞一個目標：讓簡單的做法就是正確的做法
Part 2

（vibe check）領域專業變得沒用了嗎？

提問（Matt）很多人認為大家越來越依賴 AI，領域專業就沒那麼有用了，你怎麼看？
Poteto：領域專業比以前更重要。
  • 模型越來越強（她順帶說自己很愛 Opus 5.5），瓶頸已經不在 agent，而在於你能不能把意圖和目標表達清楚，讓 agent 理解並執行
  • 現在真正的瓶頸是把意圖和願景傳給 agent
例子醫生、律師這類在非工程領域有深厚專業的人，只要稍微懂一點技術、會用 agents，腦中又有清楚的願景，就能做出很棒的產品

Matt 延伸到「語言」

  • 他著迷於字詞的組合。他最喜歡的時刻，是找到一個 agent 會「咬住」的詞，agent 會在自己的 thinking trace 裡反覆強化它
例子：TDD大家在爭論「agent 該不該用 TDD」，他認為這不重要。重點是這個詞讓 agent 去思考測試、寫測試，並用不同的方式排優先順序。他認為這也是 grilling（拷問式提問）有效的原因

Poteto 的回應

  • grilling 能把關鍵詞從你身上逼出來，或由 agent 提出那些詞，你再說「對，就是這個」
  • 她抄過 Matt 的一個 tip：減少或消除 tautological tests（同義反覆的測試）。agent 寫的大量沒用的測試是她最受不了的事之一
  • 她認為 tautology 這個詞本身就是壓縮過的意圖，一個字就承載了大量意義
  • agents 讓自然語言和程式語言交會在一起，但底層都是語言、都是溝通
  • Matt 補充自己念的是戲劇系，想語言、想莎士比亞想了很久
Part 3

為什麼用「米其林廚房」而不是「軟體工廠」？

提問（Matt）software factory 是現在最大的 buzzword，他自己也在做這方向的課。他想談的是從現在跑 1–5 個 agents，到同時跑上百個 agents 是怎麼運作的，並請 Poteto 解釋她的米其林廚房比喻

不喜歡「工廠」這個詞

  • 「工廠」不算不準確，但不會讓人聯想到品質與工藝（craft），而做產品的人很在乎使用者體驗
  • 「米其林廚房」比較有抱負感。下廚既實用（填飽肚子），也能變成藝術（讓你想起童年的一餐）

從家庭廚師到主廚

思想實驗家庭廚師一個人切菜、備料、收拾全包。這時突然把伴侶、兄弟姊妹、整個家族都塞進廚房，大部分人會壓力很大，因為這些人根本不知道器具放在哪。Matt 接話：「我的廚房容量上限是一個人。」
  • 從一個人下廚到有幾個副主廚（sous chef）幫忙，重點是有意義地切分工作，讓整體大於部分的總和，而不是為了切分而切分
  • 主廚就是廚房的 tech lead 或 CEO：何時訂食材、怎麼儲存、怎麼備料、什麼時候要備好
  • 工程師也一樣：code 由 agents 寫，但你仍要為結果負責，你的名字和聲譽仍綁在作品上
  • 你的 skills、環境、codebase，就是做產品的新食材
Part 4

Verification 具體長什麼樣子？

提問（Matt）很多人覺得 agent 已經很好、自己改善不了，也沒辦法去改 Claude Code 的內部。但其實可以改變 agent 運作的環境，例如改 codebase、給它驗證工具。你的演講非常強調 verification，它具體長什麼樣子？
「就算你不用 pstack，你工具箱裡最重要的單一 skill 也是 verification。」
  • 定義：給 agent「手和眼睛」，讓它能真的把 code 跑起來，像一般使用者一樣操作，也能 debug、取 trace 和 snapshot
  • 這是她加入 Cursor 後建的第一個 skill，也是第一個真正讓她在信任階梯上往上爬的 skill
  • 其他 skills（how、why、unslop）再好，她仍然得當 agent 與產出之間的 proxy。agent 看不到自己工作的結果，就不可能迭代
  • 她認為讓 loop 成為 loop 的最重要部分就是驗證：agent 能驗證自己的工作，人才能從等式中被拿掉
例子：agents window 效能她想做到 hill climbing：先定一個 rubric 或評分方式，有了 loop 之後，就能讓 agent 持續嘗試改進。她也提到 Karpathy 的 auto research 有類似想法
  • 現在 Cursor／SpaceX AI 的每個 app 都有自己的 verification skill，而且是自動維護的，已經成為團隊的關鍵基礎設施
Part 5

skill 裡附的 custom CLI 在做什麼？

提問（Matt）你為驗證做了一個 custom CLI，它做什麼、怎麼執行、為什麼要做？

最初的動機：context window

  • 去年底到今年初，大家最關心 context window，社群甚至有個迷因：agent 只要 compact 一次，這個 session 剩下的時間就會變笨
  • 現在 summarization 已經進步很多，比較不是為了 context，但乾淨的 context 仍然有好處

現在的核心目的：確定性和判斷力分工

  • 她用 CLI 把 skill 裡確定性（deterministic）的部分寫成 script，拿掉原本會被不必要用掉的判斷力（judgment）
  • 她把工作看成一個光譜：判斷型（需要思考、拼湊多份 context）↔ 確定型（例如把 code 從一種 pattern 重構成另一種，非常機械）
  • CLI 本身並不新奇，只是串接 Playwright、Chrome DevTools Protocol、呼叫 API 的膠水 code
  • Matt 的解讀：這是一種對 skill 隱藏資訊的方式。skill 保持精簡，等於壓縮資訊，讓 agent 的行為更一致
沒有 CLI 時的實際問題每個 agent 驗證時都會「重建整個世界」，而且每個做法都不一樣。agent 自己寫 script，結果常常不能用；上一個 agent 明明做出了能用的版本，卻把它丟掉了。這不只浪費 context，也拖慢速度
  • 給聽眾的建議：你的 skills 和 rules 裡，有多少其實可以是確定性的？讓 agent 只在非確定性的部分發揮
延伸例子：migration要遷移到對 agent 更友善的技術時，可以用 codemod 爬 AST、機械地轉換 code，由 script 來做，不必讓 agent 做
Part 6

投資環境，跟做 feature、出貨相比有多重要？

提問（Matt）如果 agent 總是在某件事上出錯，就讓那件事在環境裡不可能發生。他對好 codebase 的定義是容易修改、改了不會出事，也就是用 guardrails 把 agent 限制在很窄的路徑上。你們甚至自己做了 framework，那這件事跟做 feature 相比有多重要？
「工程師的新工作，就是花時間在環境上。」
  • 惡性循環：不投資環境，就會卡在信任階梯的低處，只能 micromanage，也就沒有餘裕去改善環境
類比：刀沒磨利就像寫 code 的年代從沒學過工具，不知道 VS Code、Vim，只會用 Notepad，連 Git 都沒聽過。刀鈍了做什麼都慢，deadline 一逼近就只能埋頭硬做
類比：壓蒜器切蒜很慢就買個壓蒜器。工具被發明是有原因的；如果米其林廚房的廚師沒有工具，每個人都會自己亂搞一套

TypeScript 與限縮空間

  • 她多年前在 TSConf 講過「限縮型別」，最喜歡的是 type narrowing：從什麼都可能的寬型別，縮小到「某個特定的 string 常數」
  • 她把這連到範疇論：codebase 的 constraints 也是在限縮可能的空間
例子：內部 framework「Dune」
  • 沒有開源，她形容它是「Electron apps 用的內部版 Next.js」，配有非常嚴格的 lint rules，一件事只有一種做法
  • 每個 feature 有自己的目錄，由 registry 爬 codebase 自動發現。效果是很難寫出爛 code，agent 也不會往 god file 裡追加
  • 起因：那個 bot 最早幾版由大約 8 個 god file 組成，每個至少一萬行
  • 方法論：觀察 agent 怎麼失敗。每看到一個錯誤就問：「怎麼把它變成 lint rule？怎麼讓 codebase 根本做不出這件事？」
  • Matt 開玩笑說 TypeScript 自己就有一個出名的 25,000 行檔案
  • Matt 的總結：要像老鷹一樣盯著 agent。規則住在環境裡，agent 不會因為要記太多規則而超載，會在對的時機撞上規則、被彈回去
Part 7

2,500 個 PR 從哪來？擴展的機制是什麼？

提問（Matt）你總不可能每個月開 2,500 個 chat。是不是有自動 trigger？software factory 怎麼自己產生工作？
  • 前提仍然是環境：如果沒先花時間經營廚房、刀具和工具，她絕對做不到
比喻：連鎖餐廳就像 Gordon Ramsay 把設計菜單的訣竅都教給行政主廚，所以能開第二、第三家店。她把每個專案、每個大 chat 看成一家餐廳，像搭直升機在它們之間巡視

inner loop 與 outer loop

  • inner loop：agent 工程師們朝著「她的意圖的 snapshot」寫 code。問題是 snapshot 會過期
  • 新的 bug report 會跑到 Slack、Linear、X 這些沒接進 inner loop 的系統，以前都是她當 proxy 轉交
  • outer loop：用那個 bot 這類工具把對外收集資訊的工作也自動化。兩個 loop 接起來，agent 就能自己取得 context
例子：Slack bug triage接 Slack MCP，或在自己的 harness 裡訂閱某個頻道，然後告訴 agent「有 bug report 就去 triage、去重現」。agent 會用 verification skill 確認 bug 在 main 上確實還存在，排除使用者 setup、資料，或沒裝 dependency 這類原因
  • 核心心法：一直問自己「這個流程裡我哪裡是瓶頸？agent 為什麼需要我來回答？」然後讓它靠真實資料，而不是幻覺自己回答
  • 她認為 company brain、context graph 這些詞不必要地複雜，說穿了就是：你原本要自己轉交給 agent 的資訊，教它自己去拿
  • 她不是坐著開 2,500 個 chat，而是用 Cursor 的新功能 Projects（coordinator agent）。它不自己做事，負責管理任務清單、spawn sub-agents
  • 最大的突破：從「怎麼讓 agent merge 自己的 code？」往回推。大家第一個反應是「你怎麼 review？團隊一定恨死你。」Matt 請她先保留這個話題，留到 Part 10
Part 8

具體來說，你的電腦畫面長什麼樣子？

提問（Matt）以前手動開 chat，就像親手把點單遞給廚師；現在像是有個 agent 在當出餐控台（expo）。是不是有 bot 訂閱頻道，再加上 coordinator 或 chief of staff agents？
  • 她承認目前的工具有點讓人困惑，團隊正在簡化與統一
  • 那個 bot 就是 outer loop：它有 connectors（很多人稱這類工具為 personal agents），可以連到 email、行事曆、Slack 等服務
  • 「context, not control」：這是她在 Netflix 時 manager 們最常談的原則。與其 micromanage，不如提供 context，讓 agent 能自給自足
具體設定幾個 bot 用 routines 持續監看她的 Slack、X、email、Linear。例如：「盯著那個 bot desktop app 的 bug，發現了就送到我的 Cursor project。」
  • Cursor Project 是一個在雲端、有自己電腦的 coordinator agent，扮演行政主廚或 chief of staff。它不做事，只負責委派、編排、傳遞 context
追問（Matt）一次湧進 30 個 issue 怎麼辦？
  • coordinator 會自己判斷用哪種 agent topology 分派最有效率
  • 分工是：Cursor Projects 負責 inner loop，那個 bot 負責 outer loop。bot 可以直接發訊息給 project，她甚至不用打開 Cursor
例子：一批效能 issue一批 issue 都在講「app 很慢」，彼此相關。如果每個 issue 開一個 agent，會失去它們之間的關聯、重複做工，也看不到更高層的問題。多份略有不同的 report 反而能幫你 zoom out：只看一份時以為 bug 在這裡，看完一整批才發現根因在更上層
Part 9

還有什麼工作來源？多久觸發一次？

提問（Matt）除了 bug report，還有其他工作來源嗎？
  • 另一個來源是讀 code。那 2,500 個 PR 不是 2,500 個 feature，很多是 gardening（園藝式的整理）
例子：新人環境夠好的話，不熟團隊工程實踐的新人第一天就能產出好 code，不會先開一堆低品質 PR
追問（Matt）觸發機制是什麼？每小時跑一次，還是用 cron job？
例子：React foot guns她有一個 agent 持續掃描被禁止的 pattern，但不叫它先修，而是叫它 append 到一份文件裡。每隔幾天她去看一次，常發現「這些其實都是同一個問題」
  • buffer／queue 的價值：處在純執行模式時會錯過大局；先累積成 artifact，人或 agent 才能從中找出 pattern
  • 這也是 chief of staff agent 的價值：除了執行，它還看得到整片森林
  • Matt 說聽到這裡腦袋有點爆炸，下週要拍的課可能得改內容
Part 10

Review：2,500 道菜你都嚐過嗎？

提問（Matt）大家最常回的就是「這些菜從你面前經過時，你每一道都嚐了嗎？」我猜答案是某種形式的「沒有」
  • 她不想變成再也不嚐自己的菜，但規模大了不可能每道都嚐，所以改成抽樣（sampling）
  • 這裡工廠比喻反而比較貼切：品質主管不檢查每一件產品，而是抽樣，並嚴格審視 agent 的壞 pattern
  • 修的是環境，不是單一 agent：一次性的錯誤可以不管；多個 agent 走同一條捷徑、到處擴散同一個 workaround 時，就去改 skills、lints、type system
她的警語達到這個境界非常難，她不想包裝成用了 pstack 就能輕鬆做到。這需要長時間觀察 agent 在哪裡失敗，有意識地設下 guardrails

這是 dark factory（關燈工廠）嗎？

Poteto：「其實某種程度上是。」
  • agent 自己 merge PR，她去睡覺時 agents 24/7 繼續工作
例子：十個以上的 chief of staff一個負責那個 bot desktop app 的效能、一個負責修使用者回報的 bug、一個在探索用另一種語言把它重寫成原生 app（純粹好玩的玩具專案）
  • 她現在是在 PR land 之後才 review
  • pstack 的 full autopilot：每個 PR 都會觸發多個 verifier agent 做 fuzz，也就是真的跑 app、像真人一樣到處點、找 regression，發現問題就自己修，重複到 PR 能 land 為止
  • 這很吃 token，但可以調整，例如把 10 個 verifier 降成 1 個，或只叫 agent 驗證自己的工作
  • 她早上看 commit history 做 review，發現問題就 revert、修改，或加新的 lint rule
  • 心理層面：第一天打開時非常可怕，擔心半夜出 SEV（嚴重事故），需要勇氣。現在她說自己「睡得好多了」

Matt 的區分：這不是 vibe coding

  • 他心中的 dark factory 接近 Karpathy 原始定義的 vibe coding：忘了 code 的存在。Poteto 的做法完全不同，code 和環境才是根本，garbage in、garbage out
  • 所以比較像調光開關，有些部分暗、有些部分亮。Poteto 補充：餐廳老闆也會偶爾回店裡嚐嚐菜
  • Matt 認為「用抽樣取代阻擋（sampling instead of blocking）」這個概念非常重要
Part 11

重視資安的領域、不可逆的變更怎麼辦？

提問（Matt）醫療、法律、金融這些領域，有的 PR 是雙向門（two-way door），merge 後可以 revert；有的是單向門（one-way door），可能造成資料遺失。如果大部分 PR 都是單向門，你還會推薦這套做法嗎？
  • 一切都回到你能從 agent 取得多好的驗證品質。可驗證的領域比較容易，某種意義上單向門會變成雙向門
  • 很難用程式驗證的領域就很難做到，所以領域的可驗證性（verifiability）是關鍵
  • 軟體工程在很多情況下相當可驗證；數學在寫證明時也有部分可以驗證
她坦白她沒有答案，這需要整個產業和工程師一起摸索
  • 她的預測：會出現越來越多為 agent 設計的程式語言（agent-oriented programming languages）
例子：Bend它把程式與形式證明結合在一起。以前證明得用 Lean、TLA+ 這類獨立語言寫，再用 solver 確認所有情況都涵蓋、沒有 race condition。她的邏輯是：如果能編譯、證明也顯示它正確，為什麼不 merge？
Part 12

pstack 跟 Matt 的 skills 要怎麼搭配使用？

提問（Matt）大家常把它想成「你的 skills vs. 我的 skills」。他把 skills 看成「被寫成文字的流程」，那要怎麼把兩邊的東西變成自己的流程？他也提到 Poteto 當天分享的 tip：翻自己過去的 transcripts，找出你不斷糾正 agent 的地方，做成 skill
  • 兩套 skills 非常互補。skill 說到底就是流程、就是 markdown，可以自由交織使用
  • 每個人都要有自己的一套刀：廚師換餐廳時都會帶著自己的刀。信任，說到底是對自己工具的信任
組合例子把 Matt 的 grill-me 和 docs、wayfinder，跟 pstack 的執行類 skills 一起用
  • 更推薦的做法是叫 agent 翻你過去的對話，找出你不得不介入的時刻，建議做成 lint rule 或新 skill。她說過去的 chats 是 context 的寶庫，是實體化的流程
例子：pstack 的 recall skill她在處理 Cursor 應用程式的 virtualization，bug 很多，每開一個新 chat 都想把上一個 chat 的 context 帶過來。recall 就是把這個 workflow 壓縮成 skill，省得每次都寫一長篇說明
  • skills 的演變：去年的 skills 比較像實作細節，例如「該用哪個確切的 script 指令」。用新模型可以把這些刪掉，專注在 workflow
  • 她預測 skills 會越來越小、越來越精簡
  • 也可以直接讀兩人的 skills 自己組合，例如把 wayfinder 和 potato mode 合成自己的 custom mode。skills 可塑性極高，因為它就只是語言
Matt：skills 裡沒有魔法。如果真有，是選用的字詞，以及把抽象流程轉成語言時所做的思考。思考一旦做完，成果就擺在那裡，別人直接拿去用就好。
  • 兩人約好可能週一再錄 Part 2

補充：值得留意的落差

  • 她自己也提了警語：達到「agent 自己 merge」需要長時間經營環境。2,500 個 PR 的前提是 Cursor 內部已有自動維護的 verification skill、Dune framework 等大量基礎設施
  • 單向門的問題沒有解答：這正好是有硬體裝置、使用者資料的產品（例如 YiBi）會碰到的邊界。要套用到團隊，應該先把「哪些變更可以驗證、可以回滾」分類清楚
  • PR 數量的性質：有大量是 gardening（清掉被禁止的 pattern、拆 god file），不能直接換算成 feature 產能
  • 時間戳是從 YouTube 自動字幕的原始時間定位的，可能有幾秒誤差。原始字幕沒有標說話者，提問者和回答者是依對話內容判斷的。
  • 字幕裡 Grockbot、grabbot、graphbot 這幾種拼法，推斷都指同一個 Cursor／SpaceX AI 的 personal-agent 產品，正式名稱未確認，內文寫成「那個 bot」。
  • 如果內嵌播放器無法載入（例如直接用 file:// 開啟時，YouTube 可能拒絕內嵌），點時間戳會改成在新分頁開啟 YouTube 的同一個時間點。
